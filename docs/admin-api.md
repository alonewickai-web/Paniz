# API مدیریت PanizStyle

همهٔ مسیرها زیر `/api/v1` هستند. عملیات مدیریتی به Bearer token نیاز دارد و فقط از Backend به MySQL دسترسی پیدا می‌کند.

## راه‌اندازی مدیر مالک

1. پس از راه‌اندازی API، کد تصادفی یک‌بارمصرف فقط وقتی هیچ مدیر مدیریتی وجود ندارد ساخته و در لاگ خصوصی سرویس API ثبت می‌شود. در Railway، آن را در **Deployments → View Logs** پیدا کنید.
2. در اپ مدیر «راه‌اندازی اولیهٔ مدیر» را بزنید و کد، نام مدیر، نام کاربری، شمارهٔ همراه بازیابی و گذرواژهٔ قوی (حداقل ۱۲ نویسه) را وارد کنید؛ یا `POST /api/v1/admin/auth/bootstrap` را فراخوانی کنید. نام کاربری پیشنهادی فرم `erfan` است و مدیر می‌تواند آن را تغییر دهد.
3. پاسخ، توکن نشست را فقط همان بار برمی‌گرداند. آن را در فضای امن سیستم‌عامل دستگاه مدیر نگه دارید؛ هش توکن در دیتابیس ذخیره می‌شود.
4. پس از ساخت مدیر، کد از دیتابیس پاک و مسیر bootstrap قفل می‌شود. کد فقط به‌صورت هش در دیتابیس نگه‌داری می‌شود و نیازی به متغیر Railway ندارد.

کد راه‌اندازی را فقط از لاگ خصوصی سرویس API بردارید و در اختیار افراد دیگر نگذارید؛ آن را در برنامهٔ Flutter، کد سایت یا مخزن Git قرار ندهید. برای سرور عمومی، ابتدا HTTPS را راه‌اندازی کنید. گذرواژه با Argon2id هش می‌شود؛ هش‌های scrypt حساب‌های قدیمی پس از ورود موفق ارتقا می‌یابند. نشست مدیر ۷ روز اعتبار دارد و با خروج یا تغییر اطلاعات ورود قابل ابطال است.

## مسیرها

| روش و مسیر | کاربرد |
| --- | --- |
| `POST /admin/auth/bootstrap` | ساخت یک‌بارهٔ مدیر مالک؛ نیازمند کد یک‌بارمصرف لاگ خصوصی API |
| `POST /admin/auth/login` | ورود با نام کاربری یا شمارهٔ همراه و گذرواژه و دریافت توکن Bearer |
| `GET /admin/auth/me` | دریافت هویت نشست جاری |
| `POST /admin/auth/logout` | ابطال نشست جاری |
| `PATCH /admin/auth/credentials` | تغییر نام کاربری و/یا گذرواژه با تأیید گذرواژهٔ فعلی؛ ابطال همهٔ نشست‌ها |
| `GET /admin/dashboard` | فروش پرداخت‌شدهٔ روز و ماه، شمار سفارش و هشدار موجودی کم |
| `GET /admin/store` | دریافت رنگ‌بندی، چیدمان، دسته‌ها و بنرهای فروشگاه |
| `PATCH /admin/store/theme` | تغییر رنگ‌بندی سایت |
| `PATCH /admin/homepage-sections/:sectionKey` | نمایش/مخفی‌کردن یا تغییر ترتیب بخش خانه (`hero`, `categories`, `products`, `story`, `benefits`) |
| `POST /admin/categories` | ساخت دستهٔ اصلی یا زیردسته (حداکثر دو سطح) |
| `PATCH /admin/categories/:id` | ویرایش نام، نشانی، تصویر، والد، ترتیب یا فعال‌بودن دسته |
| `DELETE /admin/categories/:id` | بایگانی دسته بدون حذف سوابق محصولات |
| `POST /admin/banners` | ساخت بنر فعال یا زمان‌بندی‌شده برای صفحهٔ اصلی |
| `PATCH /admin/banners/:id` | ویرایش تصویر، متن، مقصد، بازهٔ نمایش یا فعال‌بودن بنر |
| `DELETE /admin/banners/:id` | حذف بنر |
| `GET /admin/products?page=&pageSize=&status=&q=` | جست‌وجوی محصولات منتشرشده، پیش‌نویس یا بایگانی‌شده |
| `POST /admin/products` | ایجاد محصول، تصاویر و تنوع‌های اولیه؛ وضعیت پیش‌فرض پیش‌نویس |
| `PATCH /admin/products/:id` | ویرایش عنوان، نشانی، دسته، توضیح و انتشار/پیش‌نویس |
| `DELETE /admin/products/:id` | بایگانی نرم؛ سابقهٔ سفارش حفظ می‌شود |
| `POST /admin/products/:id/variants` | افزودن ترکیب رنگ و سایز و ثبت موجودی اولیه |
| `POST /admin/products/:id/images` | افزودن مسیر محلی سایت یا HTTPS به گالری محصول |
| `DELETE /admin/products/:id/images/:imageId` | حذف تصویر؛ محصول باید دست‌کم یک تصویر داشته باشد |
| `PATCH /admin/products/variants/:variantId` | ویرایش قیمت، قیمت پیش از تخفیف و آستانهٔ هشدار تنوع |
| `GET /admin/orders?page=&pageSize=&status=&q=` | فهرست صفحه‌بندی‌شدهٔ سفارش‌ها |
| `PATCH /admin/orders/:id/status` | تغییر وضعیت مجاز، ثبت تاریخچه و کد رهگیری |
| `PATCH /admin/inventory/variants/:variantId` | تغییر موجودی با `delta` مثبت/منفی و دلیل اجباری |
| `GET /storefront/config` | دریافت رنگ‌بندی عمومی، بخش‌های فعال خانه و بنرهای داخل بازهٔ نمایش |

برای همهٔ مسیرهای به‌جز ورود و bootstrap، هدر `Authorization: Bearer <accessToken>` بفرستید. تغییر موجودی، وضعیت سفارش و اطلاعات محصول در `admin_audit_logs` ثبت می‌شود. کاهش موجودی نمی‌تواند از تعداد رزروشده کمتر شود.

## محدودیت‌های گردش سفارش

- سفارش پرداخت‌نشده را می‌توان لغو کرد؛ رزرو انبار در همان تراکنش آزاد می‌شود.
- مراحل تأیید، آماده‌سازی، ارسال و تحویل فقط پس از ثبت پرداخت تأییدشده در Backend پذیرفته می‌شوند.
- گذار به «ارسال‌شده» به کد رهگیری نیاز دارد.
- اتصال درگاه پرداخت و webhook تأیید تراکنش هنوز پیاده نشده است؛ مدیر نمی‌تواند از API مدیریتی سفارش را پرداخت‌شده اعلام کند.
